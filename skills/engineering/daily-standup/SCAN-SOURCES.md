# SCAN-SOURCES.md

What to scan, how to scan it, and how to convert findings into candidate work items. Organized by source. Run these in parallel during Step 1 of the process.

---

## GitHub issues

**Goal:** Find open work that is available, blocked-and-now-unblocked, or stale enough to need triage.

**Commands:**

```bash
# All open issues with labels and assignees
gh issue list --state open --limit 50

# Issues labeled as bugs (highest priority)
gh issue list --state open --label bug --limit 20

# Issues with no assignee (available work)
gh issue list --state open --assignee "" --limit 20

# Issues with recent comments (activity = progress or new info)
gh issue list --state open --sort updated --limit 10

# Oldest open issues (staleness check)
gh issue list --state open --sort created --limit 10
```

**How to interpret:**

- **Bugs with no assignee** — these are the highest-priority available work. Someone reported a problem and nobody is fixing it.
- **Issues open longer than 30 days** — either the issue is parked (in which case it should be labeled or closed) or it is being neglected. Both are signals.
- **Issues with recent comments but no PR** — discussion is happening but work is not. May need unblocking or someone to just start.
- **Issues labeled "ready-for-agent", "good-first-issue", or similar** — explicitly available for autonomous work.

**What to ignore:**

- Issues explicitly labeled "parked", "wontfix", "on-hold", or "icebox"
- Feature requests with no triage (no labels, no comments beyond the original)
- Issues in other repositories (unless the user scoped the standup to a monorepo)

**Converting to candidate work items:**

Each actionable issue becomes a candidate. Include the issue number, title, age, and labels in the candidate. If multiple issues relate to the same subsystem, group them into a single candidate work item.

## Recent commits

**Goal:** Find unfinished work, hot spots, and patterns that need propagation or cleanup.

**Commands:**

```bash
# Recent commits (last 3 days)
git log --oneline --since="3 days ago"

# Files changed most frequently (hot spots)
git log --since="3 days ago" --name-only --pretty=format: | sort | uniq -c | sort -rn | head -20

# Commits with WIP/temp/hack markers
git log --oneline --since="7 days ago" --grep="WIP\|wip\|temp\|hack\|fixme\|TODO\|quick fix\|hotfix"

# Large recent diffs (possible incomplete refactors)
git log --since="3 days ago" --stat --diff-filter=M | head -50

# New files without corresponding tests
git log --since="3 days ago" --name-only --diff-filter=A --pretty=format: | sort -u

# What was worked on yesterday specifically (carryover check)
git log --oneline --since="1 day ago"
```

**How to interpret:**

- **Files touched multiple times** — these are hot spots. Frequent changes suggest the code is either being actively developed (fine) or repeatedly patched (needs refactoring).
- **WIP/temp/hack in commit messages** — the author knew this was incomplete. Follow up.
- **Large diffs on a single file** — may indicate an incomplete refactor, or a god component getting larger.
- **New files with no test counterpart** — new code shipped without test coverage.
- **Yesterday's commits** — carryover check. If work was started but not finished, it should appear in today's plan.

**What to ignore:**

- Merge commits (noise in the signal)
- Dependency updates (`package-lock.json`, `yarn.lock`) unless the commit message mentions breaking changes
- Auto-generated files (migrations generated by a tool, lockfiles, build artifacts)

**Converting to candidate work items:**

- Hot spot files become "refactor [file]" candidates
- WIP commits become "finish [feature]" candidates
- New files without tests become "add tests for [file]" candidates
- Incomplete refactors become "complete [refactor]" candidates

## Codebase signals

**Goal:** Surface technical debt, quality gaps, and maintenance needs that are not tracked in issues.

### TODOs and FIXMEs

```bash
# Count and categorize
grep -rn "TODO\|FIXME\|HACK\|XXX" --include="*.ts" --include="*.tsx" --include="*.js" --include="*.jsx" --include="*.py" --include="*.rb" --include="*.go" . | grep -v node_modules | grep -v ".git/"

# Structural TODOs (high priority — affect safety)
grep -rn "TODO.*error\|TODO.*auth\|TODO.*valid\|TODO.*secur\|TODO.*handl\|FIXME\|HACK\|XXX" --include="*.ts" --include="*.tsx" --include="*.js" --include="*.jsx" --include="*.py" . | grep -v node_modules
```

**Interpretation:** FIXME/HACK/XXX are always worth reviewing. TODOs mentioning error handling, auth, validation, or security are structural debt. TODOs about features belong in the issue tracker, not in the code.

### Large files

```bash
# Source files sorted by line count (top 20)
find . -name "*.ts" -o -name "*.tsx" -o -name "*.jsx" -o -name "*.py" -o -name "*.rb" -o -name "*.go" | grep -v node_modules | grep -v ".git" | xargs wc -l 2>/dev/null | sort -rn | head -20
```

**Interpretation:** Files over 300 lines are candidates for decomposition. Files over 500 lines are almost certainly doing too much. Cross-reference with hot spots — a large file that is also frequently changed is the highest-priority refactoring target.

### Files without tests

```bash
# Compare source files to test files (adjust paths for project structure)
# Find source files
find src -name "*.ts" -o -name "*.tsx" | grep -v ".test.\|.spec.\|__test__" | sort > /tmp/src_files.txt 2>/dev/null

# Find test files
find . -name "*.test.*" -o -name "*.spec.*" | sort > /tmp/test_files.txt 2>/dev/null

# Count source vs test files
echo "Source files: $(wc -l < /tmp/src_files.txt)"
echo "Test files: $(wc -l < /tmp/test_files.txt)"
```

**Interpretation:** A test-to-source ratio below 0.5 indicates significant coverage gaps. Focus on recently changed files without tests — they are the most likely to regress.

### Recent changes without tests

```bash
# Files changed in last 3 days that are not test files
git log --since="3 days ago" --name-only --pretty=format: | sort -u | grep -v "test\|spec\|__test__" | grep -v "^$"

# Cross-reference: do these files have corresponding test files?
```

**Interpretation:** Recent changes to source files with no corresponding test changes = untested new behavior. High-priority candidate for "add tests" work items.

### Dependency audit

```bash
# npm projects
npm audit 2>/dev/null | tail -20

# Python projects
pip audit 2>/dev/null || safety check 2>/dev/null

# Go projects
go list -m -json all 2>/dev/null | head -50
```

**Interpretation:** Critical and high-severity vulnerabilities are work items. Moderate and low can be batched into a "dependency maintenance" item if there are many.

### Lint warnings

```bash
# Run the project's linter (detect which one is configured)
npx eslint . --format compact 2>/dev/null | tail -20
npx tsc --noEmit 2>/dev/null | tail -20
```

**Interpretation:** Lint warnings cluster by category. A handful of "unused variable" warnings is low priority. Dozens of "any type" warnings indicate a systematic type safety gap.

### Type gaps (TypeScript projects)

```bash
# Explicit any usage
grep -rn ": any\|as any\|: any\[\]" --include="*.ts" --include="*.tsx" . | grep -v node_modules | wc -l

# TypeScript suppressions
grep -rn "@ts-ignore\|@ts-expect-error" --include="*.ts" --include="*.tsx" . | grep -v node_modules
```

**Interpretation:** High `any` count relative to codebase size means types provide no real safety. `@ts-ignore` means someone suppressed a real error instead of fixing it.

## Cross-skill signals

Quick checks that other skills would catch during a full audit. These are not full audits — they are lightweight scans for the most common issues.

### Empty states (from audit-empty-states)

```bash
# Generic empty state strings
grep -rn "No results\|Nothing here\|No data\|No items\|Empty\|Nothing to show" --include="*.ts" --include="*.tsx" --include="*.jsx" . | grep -v node_modules | grep -v ".test.\|.spec."
```

**Interpretation:** Generic empty states are missed product opportunities. Each one should guide the user to their next action.

### Error copy (from error-copy-review)

```bash
# Generic error messages
grep -rn "Something went wrong\|An error occurred\|Error:\|Unexpected error\|Please try again" --include="*.ts" --include="*.tsx" --include="*.jsx" . | grep -v node_modules | grep -v ".test.\|.spec."
```

**Interpretation:** Generic error messages leave users helpless. Each should explain what happened and how to recover.

### Security quick check (from security-review)

```bash
# Potential hardcoded secrets
grep -rn "sk-\|pk_\|AKIA\|ghp_\|xoxb-\|password.*=.*['\"]" --include="*.ts" --include="*.tsx" --include="*.js" --include="*.jsx" --include="*.env*" . | grep -v node_modules | grep -v ".test.\|.spec."

# Environment variables in client-side code
grep -rn "process\.env\." --include="*.tsx" --include="*.jsx" . | grep -v node_modules | grep -v "NEXT_PUBLIC\|REACT_APP\|VITE_"
```

**Interpretation:** Hardcoded secrets are always critical. Server-side env vars in client code may indicate leaked configuration.

### Dead code

```bash
# Large commented-out blocks
grep -rn "^[[:space:]]*//" --include="*.ts" --include="*.tsx" --include="*.js" --include="*.jsx" . | grep -v node_modules | awk -F: '{print $1}' | uniq -c | sort -rn | head -10

# console.log left in production code
grep -rn "console\.log\|console\.debug" --include="*.ts" --include="*.tsx" --include="*.js" --include="*.jsx" . | grep -v node_modules | grep -v ".test.\|.spec." | wc -l
```

**Interpretation:** Files with many comment lines likely contain dead code. Console.log in production code is debug residue that should be removed or replaced with structured logging.

## Scan order and parallelism

Run these groups in parallel:

1. **Group A (external state):** GitHub issues via `gh` CLI
2. **Group B (git history):** Recent commits, hot spots, WIP detection
3. **Group C (codebase):** TODOs, large files, type gaps, lint warnings
4. **Group D (cross-skill):** Empty states, error copy, security, dead code

Each group takes 30-60 seconds. Running in parallel, the full scan completes in under 2 minutes. Do not attempt to run dependency audits or linters if they take more than 30 seconds — note them as "skipped, too slow" and move on.
